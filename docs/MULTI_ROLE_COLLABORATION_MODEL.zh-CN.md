# 多角色协作体模型

## 核心构想

用户设想的 Agent 更偏向一个工作协作体，而不是单一助手。

系统以“项目”作为主要输入和输出口。项目负责承接用户目标、维护上下文、协调不同工种角色，并汇总最终输出。不同角色以专业分工的方式参与工作，例如项目、产品、技术、开发、测试，后续还可能扩展设计、视频、音频等角色。

## 初始角色

### 项目角色

项目角色是输入和输出口，也是协作调度中心。

职责：

- 接收用户需求。
- 明确目标、范围、约束和交付物。
- 拆分任务并分派给不同角色。
- 维护项目级上下文和状态。
- 汇总各角色产出。
- 向用户输出阶段性结果和最终结果。

### 产品角色

产品角色关注需求、用户价值和产品定义。

职责：

- 澄清需求。
- 定义用户场景和使用流程。
- 输出需求说明、功能范围和验收标准。
- 判断功能优先级。
- 与技术和开发角色对齐可实现性。

### 技术角色

技术角色关注架构、技术方案和工程约束。

职责：

- 设计系统架构。
- 评估技术选型。
- 拆分模块边界。
- 识别风险和复杂度。
- 为开发角色提供实现方案。

### 开发角色

开发角色关注代码实现和工程落地。

职责：

- 根据产品和技术方案实现功能。
- 修改代码、补充测试、处理构建问题。
- 维护代码质量和可读性。
- 输出实现说明和变更摘要。

### 测试角色

测试角色关注质量、验收和边界情况。

职责：

- 根据需求和实现设计测试点。
- 验证功能是否满足验收标准。
- 发现回归、缺陷和遗漏。
- 输出测试结果和风险提示。

## 后续可扩展角色

未来可以继续增加：

- 设计角色：交互、视觉、体验规范、原型。
- 视频角色：脚本、分镜、剪辑方案、素材规划。
- 音频角色：配音、音效、音乐、播客或音频内容制作。
- 运营角色：发布计划、增长策略、内容运营。
- 数据角色：指标、分析、实验和报表。

## 协作方式

建议把协作流程建模为：

1. 用户向项目入口提交目标。
2. 项目角色整理需求和上下文。
3. 项目角色决定需要哪些角色参与。
4. 各角色基于自己的职责产出专业结果。
5. 项目角色整合角色产出，处理冲突和缺口。
6. 必要时进入下一轮澄清、实现或验证。
7. 项目角色向用户输出结果。

## 架构含义

这个构想意味着系统核心不应只是一个 Agent Loop，而应支持“项目 + 角色 + 任务 + 产出”的协作模型。

因此前期技术选型需要优先保证这些核心对象能被稳定表达和扩展。语言、运行时、仓库结构、存储方式和工具权限模型会影响长期架构，应尽早确定；具体 UI 组件库、队列、向量库等可以后置。

关键对象可能包括：

- Project：项目上下文、目标、状态、输入输出口。
- Role：角色定义、职责边界、提示词、工具权限。
- Task：项目拆分出的具体任务。
- Artifact：角色产出的文档、代码、设计、测试报告等。
- Handoff：角色之间的交接信息。
- Review：角色对其他产出的审查和反馈。

## 早期实现建议

第一阶段不需要做复杂的多智能体并发系统。可以先做“单进程、多角色模拟”：

- 项目角色作为主控。
- 角色先用配置文件定义，包括名称、职责、系统提示词、可用工具。
- 同一个模型在不同角色提示词下轮流工作。
- 每个角色输出结构化结果。
- 项目角色负责汇总和推进状态。

这样可以先验证协作模型是否有用，再考虑并行多 Agent、角色记忆、角色私有工具和复杂调度。

## 需要继续确认的问题

- 项目角色是否应该始终作为唯一输入输出口，还是允许用户直接点名某个角色？
- 角色之间是否可以互相发起请求，还是必须通过项目角色协调？
- 第一版要支持哪些角色？
- 角色产出应该保存成 Markdown、JSON，还是数据库记录？
- 多角色协作是同步轮次制，还是异步任务制？
