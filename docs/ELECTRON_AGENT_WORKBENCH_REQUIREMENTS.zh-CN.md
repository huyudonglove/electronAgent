# Electron Agent 工作台需求草案

## 产品定位

项目目标调整为一个类似 Codex 的 GUI 工具，但核心不是单一聊天助手，而是一个桌面端多角色 Agent 编排工作台。

用户希望：

- 使用 Electron 作为桌面壳。
- 拥有类似节点操作的可视化编排方式。
- 主要实现角色扮演式 Agents 编排。
- 支持串行和并行执行相关 Agents 任务。
- 以项目作为输入、输出和协作管理口。

## 核心体验

第一版工作台应围绕“项目 + 编排画布 + 运行记录”组织。

建议主界面包括：

- 项目列表 / 工作区选择。
- 当前项目上下文。
- 节点式 Agent 编排画布。
- Chatbot 项目协作入口。
- 角色库。
- 任务运行面板。
- 每个节点的输入、输出、日志和状态。
- 产出物列表，例如需求文档、技术方案、代码变更、测试报告。

Chatbot 不替代节点画布。它负责自然语言协作、项目上下文问答、生成或调整工作流草案、触发当前工作流运行、解释角色产出，并通过 Model Provider Registry 接入不同模型。

## 节点编排模型

画布中的节点不只是视觉元素，而是可执行单元。

建议第一版节点类型：

- Start：项目输入入口。
- Role Agent：角色节点，例如产品、技术、开发、测试。
- Human Approval：人工确认节点。
- Tool Action：工具动作节点，例如读文件、搜索、Shell、Git。
- Merge：汇总多个上游结果。
- Decision：根据条件选择后续路径。
- Artifact Output：保存产出物。
- End：流程结束。

## 串行与并行

编排引擎需要支持有向无环图优先的执行模型。

第一版建议：

- 上游节点完成后，下游节点才可执行。
- 多个无依赖节点可以并行执行。
- Merge 节点等待多个上游节点全部完成。
- 节点失败后流程暂停，并允许重试、跳过或人工修复。
- 每次运行都生成可追踪的 run 记录。

后续再考虑循环、条件分支、动态生成节点和长时间后台任务。

## 角色扮演式 Agents

角色应是可配置对象，而不是硬编码逻辑。

每个角色至少包含：

- 角色名称。
- 职责描述。
- 系统提示词。
- 可用工具权限。
- 输入要求。
- 输出格式。
- 可交接给哪些角色。
- 默认模型配置。

初始角色建议：

- 项目经理 / 项目角色。
- 产品经理。
- 技术架构师。
- 开发工程师。
- 测试工程师。

未来扩展：

- 设计师。
- 视频策划。
- 音频制作。
- 运营。
- 数据分析。

## 推荐技术路线

### 桌面壳

使用 Electron。

建议安全基线：

- Renderer 不直接开启 Node.js 能力。
- 使用 preload 暴露受控 API。
- 使用 IPC 让 Renderer 请求主进程或 Core 执行本地能力。
- 对文件、Shell、Git、网络工具做权限控制。

### 前端

建议使用 React + React Flow/xyflow。

原因：

- 适合构建节点式编辑器和交互式流程图。
- 节点、边、连接点、画布交互都已有成熟抽象。
- 可以自定义角色节点、工具节点、审批节点和汇总节点。

### Core

Agent Core 仍应独立于 Electron 和 UI。

Core 负责：

- Chat Service。
- Model Provider Registry。
- Workflow 编译和执行。
- Agent/Role 运行。
- 模型 Provider 调用。
- 工具调用。
- 权限检查。
- 任务状态。
- 运行日志。
- 产出物保存。

Electron 只是壳，不能把 Agent 编排逻辑写死在 Renderer 里。

### 编排引擎

第一版建议自研轻量 DAG 执行器。

原因：

- 项目早期需要完全理解自己的节点、角色和权限模型。
- 角色编排和 GUI 画布的数据结构需要紧密对齐。
- 自研 DAG 执行器足够支撑串行、并行、失败暂停、重试和合并。

后续当需要更强的状态持久化、长任务恢复、人类介入、复杂多 Agent 图执行时，再评估接入 LangGraph 或队列系统。

## 核心数据对象

建议前期定义这些对象：

- Workspace：本地工作区。
- Project：项目，负责输入输出和上下文。
- Role：角色定义。
- AgentNode：画布中的可执行角色或动作节点。
- Edge：节点依赖关系。
- Workflow：节点和边组成的编排图。
- Run：一次流程运行。
- NodeRun：单个节点的一次运行记录。
- Artifact：产出物。
- ToolCall：工具调用记录。
- PermissionPolicy：权限策略。

## 第一版 MVP

建议第一版只做一个最小但完整的闭环：

1. 创建项目。
2. 创建或选择角色。
3. 在画布中连接 3-5 个节点。
4. 从 Start 输入需求。
5. 产品、技术、开发、测试角色按图执行。
6. 支持两个角色并行执行。
7. Merge 节点汇总结果。
8. 保存运行日志和产出物。
9. 在 GUI 中查看每个节点状态、输入、输出、错误和重试按钮。

## 暂不做

第一版先不做：

- 复杂循环图。
- 插件市场。
- 多人协作。
- 云端同步。
- 大规模任务队列。
- 向量数据库。
- 自动发布应用。
- 完整权限管理后台。

## 需要继续细化的问题

- 画布是只用于“设计流程”，还是运行时也实时显示状态？
- 用户是否可以直接编辑每个角色的提示词？
- 角色节点是否允许绑定不同模型？
- 并行节点失败时，是全部停止，还是只暂停相关分支？
- 项目产出物保存为 Markdown/JSON 文件，还是同时写入 SQLite？
- 第一版是否必须支持 Shell/Git 工具，还是先只支持纯文本 Agent 协作？
- 是否需要在节点之间传递结构化 JSON，而不是自然语言文本？
