# 个人 AI Agent 搭建路线图

## 一句话目标

先搭建一个能稳定帮用户完成真实任务的个人 Agent，再逐步扩展成以项目为入口、由多角色协作完成工作的长期系统。

## 需要做的事情

### 1. 明确个人场景

先回答这个 Agent 主要替用户做什么，而不是先选框架。

需要明确：

- 高频任务：写代码、查资料、整理文档、自动化操作、项目管理、内容生成等。
- 使用入口：CLI、Web、桌面端、微信/企微、浏览器插件等。
- 自动化程度：只给建议、半自动执行、还是允许它直接改文件和调用工具。
- 安全边界：哪些事情必须确认，哪些事情可以自动执行。

### 2. 设计最小可用 Agent 核心

第一版核心应保持简单，重点是跑通闭环。

前期需要先确定会影响架构边界的技术选型，例如语言运行时、仓库结构、Core 与 UI 的边界、多角色数据模型、存储方式、模型 Provider 抽象和工具权限模型。具体 UI 组件库、向量库、队列系统、桌面壳等可以延迟。

建议包含：

- 模型调用层：封装不同模型或服务商。
- 消息与上下文管理：维护当前对话、系统提示、任务状态。
- 工具调用层：定义工具 schema、执行工具、返回结果。
- 执行循环：模型思考、选择工具、执行、观察结果、继续或结束。
- 日志记录：记录每次模型请求、工具调用、错误和结果。
- 角色执行上下文：支持用不同角色提示词和职责边界处理同一个项目任务。

### 3. 建立记忆系统

个人 Agent 的价值很大一部分来自“记得你是谁、你怎么工作、项目现在到哪里了”。

建议分层：

- 项目记忆：项目规则、架构决策、长期方向。
- 用户偏好：语言、风格、工作习惯、确认偏好。
- 会话摘要：长对话压缩后的关键上下文。
- 知识库记忆：文档、笔记、资料、代码库说明。

早期可以先用 Markdown/JSON 文件，后面再接数据库或向量库。

### 4. 建立工具系统

工具是 Agent 从“聊天”变成“做事”的关键。

早期工具可以包括：

- 文件读写。
- Shell 命令执行。
- Git 状态与差异查看。
- 项目搜索。
- 文档生成和更新。
- Web/API 请求。

工具系统需要有权限控制、执行日志、错误处理和用户确认机制。

### 5. 建立任务规划能力

不要一开始追求复杂自治，先做可解释、可暂停、可恢复的任务流程。

建议支持：

- 把目标拆成步骤。
- 标记步骤状态。
- 每一步可查看、可修改。
- 失败后能说明原因并调整计划。
- 长任务能保存进度。
- 支持项目角色将任务分配给产品、技术、开发、测试等角色。

### 5.1 建立多角色协作模型

用户希望 Agent 更像一个工作协作体，由项目角色作为输入输出口，协调不同工种角色完成工作。

第一版建议支持：

- 项目角色：承接用户输入、拆分任务、协调角色、汇总输出。
- 产品角色：澄清需求、定义范围、输出验收标准。
- 技术角色：设计架构、评估方案、识别风险。
- 开发角色：实现功能、修改代码、处理构建问题。
- 测试角色：设计测试点、验证结果、指出风险。

未来可以扩展设计、视频、音频、运营、数据等角色。

早期实现不需要复杂并发多 Agent。可以先用“单进程、多角色模拟”：同一个模型在不同角色提示词下轮流执行，项目角色负责调度和汇总。

### 6. 建立 Skill / 插件机制

当某类任务重复出现时，把它沉淀成 Skill 或插件。

适合沉淀的内容：

- 项目协作规则。
- 特定领域工作流。
- 常用工具组合。
- 固定文档模板。
- 特定平台 API 操作方式。

当前仓库已经有 `skills/personal-agent-project/`，它是项目专属 Skill 的第一版。

### 7. 选择交互界面

用户已经明确希望使用类似 Codex 的 Electron GUI 工具，因此第一版界面方向调整为 Electron 工作台。

可选路径：

- CLI：仍可作为调试和自动化入口。
- Electron GUI：主要产品形态，适合本地项目、工具调用、节点编排和运行记录。
- React Flow/xyflow 节点画布：用于角色 Agent 编排。
- 消息入口：适合随手触发和通知，但不适合作为第一版核心。

当前建议：做 Electron GUI，但 Agent Core 必须与 UI 解耦。Renderer 负责显示和交互，Core 负责 Agent、角色、工具、记忆和编排执行。

### 8. 做安全和权限边界

个人 Agent 能访问本地文件和工具时，安全边界必须清楚。

需要设计：

- 哪些工具默认禁用。
- 哪些操作需要用户确认。
- 文件访问范围。
- 命令执行白名单或审批机制。
- 敏感信息保存方式。
- 工具调用审计日志。

### 9. 工程化

当核心闭环可用后，再补工程化。

包括：

- 配置系统。
- 测试。
- 错误处理。
- 日志和追踪。
- 数据迁移。
- 插件加载。
- 文档。
- 发布和部署。

## 推荐推进顺序

1. 先确定 3 个真实使用场景。
2. 搭一个 CLI 版最小 Agent。
3. 接入模型调用和基础对话。
4. 加入文件读写、搜索、Shell、Git 等基础工具。
5. 加入本地 Markdown/JSON 记忆。
6. 加入任务计划和状态记录。
7. 把重复流程沉淀成 Skill。
8. 再考虑 Web UI 或桌面端。

## 第一阶段建议

第一阶段目标不是“做一个全能 Agent”，而是做一个能在本仓库里协助用户长期搭项目的 Agent。

第一阶段可以实现：

- 项目记忆读写。
- 任务计划文件。
- 基础工具注册系统。
- 模型调用封装。
- CLI 对话入口。
- 工具调用日志。
- 基础角色定义文件。
- 项目角色调度产品、技术、开发、测试角色的最小流程。

这样可以很快形成一个真实可用的闭环。
